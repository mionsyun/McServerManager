# Template inspection and dependency planning: first milestone

## Delivered boundary

This is a read-only preview milestone with an offline parser and planner, not the complete template MVP.
The existing Java creation window's import page can inspect a local
`.maipilot-template.json`. The inspection operation never provisions a server, resolves a provider,
downloads an addon, executes a JAR, changes network settings, or starts a server.
Existing manual creation, backup, and server controls are not rerouted.
The host creation wizard retains its pre-existing startup behavior: it may
request the Minecraft version list and locate Java (including `where.exe`)
before a route is selected. Those operations do not use manifest contents;
this milestone does not promise an entirely offline host window. No inspected
JAR, template-provided command, or runtime is executed by inspection.

A successful preview means **format and local consistency checks passed**. It
is not a safety verdict, verified origin, compatibility guarantee, or a runnable
recipe. Runtime releases and builds in fixtures are structural examples, not a
maintained or recommended catalog. There is no official template catalog yet.

## Manifest contract

- UTF-8 JSON schema version `1.0`; unknown fields, duplicate properties,
  comments, trailing data, unsupported versions and invalid Unicode are rejected
- Exact runtime identities: Vanilla Minecraft version; Paper version + build;
  Fabric version + loader + installer; Forge version + build
- Only difficulty, game mode, maximum players, view/simulation distances, PvP,
  and spawn protection are shared settings
- No template-provided paths, URLs, scripts, JVM arguments, credentials,
  security settings, ports, or executable inspection
- Addon references use explicit provider/project/version/file/hash identities;
  file names receive Windows-safe checks even when tests run on Linux
- CurseForge remains disabled pending its API and persistence permissions
- Original-byte SHA-256 is computed for future inspection/commit binding

Schema recognition does not enable applying any runtime. In particular, Forge
recognition does not mean that a Forge adapter is implemented. The application's
existing runtime download API does not yet accept every required fixed pin, so
it must not be reused to silently fetch a newer runtime for a template.

### Application-owned limits

| Resource | Limit |
|---|---:|
| Manifest | 1 MiB UTF-8 |
| JSON nesting | 16 |
| Addons | 256 |
| Dependency path | 16 artifact entries |
| Planner declarations / bindings | 4096 |
| Declared individual addon | 512 MiB |
| Declared total addons | 2 GiB |
| Runtime version fields | 96 characters |
| Maximum players | 1–1000 |
| View / simulation distance | 2–32 |
| Spawn protection | 0–256 |

Declared sizes and pins are not downloaded or independently verified in this
milestone. Target-version setting support must be checked before future apply.
Limits cannot be relaxed by a template.

## Dependency planner boundary

The separate pure planner takes injected evidence and explicit identities. It
has no provider client or JAR reader. Its results must not be presented as
verified live metadata: a future acquisition layer must substantiate every
input against permitted provider responses and bounded non-executing metadata
inspection first. Required metadata and exact-version constraints fail closed
when unknown, missing or conflicting; unsupported ranges are not guessed.
Installed files are never silently removed, downgraded or replaced. Platform
identities and Fabric mod IDs are distinct from provider project IDs.

No operation generated by the planner is applied by this milestone. Tests use
synthetic evidence, not live MODs, and prove planning behavior only.

## Tests

Cross-platform production-source tests:

    dotnet test McServerManager.TemplateTests/McServerManager.TemplateTests.csproj -c Release

WPF cross-build from Linux (compile only):

    dotnet build McServerManager/McServerManager.csproj -c Release -p:EnableWindowsTargeting=true

The test project links the exact production parser, planner, and inspection
ViewModel sources; it does not maintain a second implementation. Inspection
state tests cover cancellation, a slow obsolete result after a newer selection,
read failure, and format-only success wording.

Windows release qualification remains separate: WPF rendering, keyboard and
screen-reader behavior, 100/150/200% DPI, dialog cancellation and repeated
selection, navigation while reading, and normal creation/backup/server-control
regression checks. No real server launch or network opening is part of this
milestone's automated tests.

## Required next stages before template creation

1. Exact official runtime adapters, maintained runtime/version capability table,
   and corresponding contract tests
2. Authorized provider resolution and permitted file/hash verification; bounded
   non-executing Fabric metadata inspection, alias/nested evidence handling,
   and loader-specific version semantics
3. Review of an immutable change plan tied to inspected bytes and settings
4. Isolated staging, destination validation, atomic commit/registration,
   cancellation/cleanup and failure-recovery tests
5. Stopped completion view and Windows end-to-end creation/start/join checks

Only after these stages may shared template application or automatic
prerequisite addition be enabled. No billing, authoring entitlement, or public
release behavior is implemented here.
